# Build Proof to Model Assets

## When to use

Use when PROOF_TO_MODEL is resolved for 2D-to-3D asset production or when resuming its staged native workflow. Do not invoke reconstruction for ordinary CSS/SVG interfaces or silently change a selected pipeline.

## Workflow

1. Read architecture, STYLE.md, `.styles/.pipelines/proof-to-model/PIPELINE.md` and its recipe/toolchain/schema. Resolve selection with `select-art-pipeline`, recording prompt evidence when applicable.
2. Inspect configured libraries with `use-external-asset-library`; preserve repository-local copy receipts and ancestry. Record scale, interfaces, rights, geometry/texture/collision budgets and rigging/animation applicability.
3. Consult command/subcommand help and verify the installed native/host capability before selecting a conditioning profile. Default `init` registers v2 six-view `multi-view`. Explicit `init --mode multi-view-four --conditioning-profile PATH` requires the separately qualified `cardinal-four-v1` profile and a fresh v3 manifest; it is not selected from image count or on six-view failure. Retain the accepted base toolchain and installation evidence unchanged. Continuations use that manifest's registered profile; an optional `--mode` must match and cannot change it. Use `init` to preserve authorized originals; use `doctor` and dry-run `setup` to inspect prerequisites. Execute setup only with explicit authorization and license evidence. Never accept licenses or install drivers.
4. First inspect and research only the registered original images. Read [source-subject-classification.md](references/source-subject-classification.md) for entities, observed/inferred anatomy or structure, materials, occlusion and unresolved interpretations. Register the actual report with `classify`; native registration does not perform vision or research.
5. Read [multiview-proof-contract.md](references/multiview-proof-contract.md) to plan one pose, identity and camera convention. Six-view slots are front, subject-right, back, subject-left, top and bottom; the explicitly registered four-view profile uses only the first four cardinal slots. For the six-view default, a sole usable canonical source needs five missing views; an oblique/cropped source remains an anchor and may require six. For four-view, budget only missing selected cardinal views and explicitly retain polar coverage as unknown. New images/revisions require explicit CLOUD/LOCAL selection, MEDIA.md, rights and bounded spending authorization; profile selection alone grants none. Use the available session media capability, then register actual artifacts with `prepare-proofs`; the native command is not an image generator.
6. Show originals and every current proof in the selected profile, resolve consequential inferred features, and obtain human approval bound to that exact complete set, classification, cameras and profile. Preserve rejected candidates and revise only selected views. Record `proof-set` approval before `preprocess` using the current `status` fingerprint named `proofSet`; a six-view receipt cannot approve four-view, or vice versa. Preserve real alpha or explicit BiRefNet, every mask, common square padding and adjusted camera FOV. A genuine technical reviewer may inspect and approve actual preprocessing against its current fingerprint; do not invent a human preprocessing milestone. `reconstruct` consumes exactly six or four distinct prepared images, matching transforms/count and the verified MV weights for the registered profile.
7. Run `finish` for UV/bake, LOD/collision and editable blend/GLB outputs. Default finishing requires measured successful QuadriFlow; optional schemaVersion1 settings may select bounded working-low preparation. For explicitly selected rigid/articulated finishing, read [rigid-part-finishing.md](references/rigid-part-finishing.md): schemaVersion2 consumes reviewed authored HIGH/LOW pairs, exact part/repair ancestry and a supported native memory policy. Preserve the detailed high sources, actual material/atlas correspondence and all budgets. Settings never rewrite conditioning contracts, relax failed bounds or select a fallback automatically. Use only the fixed audited/hash-bound Blender 4.5 LTS bundle; this exception does not authorize arbitrary batch scripts or relax standalone BLENDER rules.
8. Run `review` and `validate`; inspect independent re-import findings and original-source comparisons. Six-view review has six matching-camera proof/render pairs; four-view review has four cardinal pairs plus separately labeled unpaired top/bottom model-only diagnostics. Omitted polar surfaces, hands, soles, cloth and occluded joints need actual geometry review; a phantom/transparent material cannot repair anatomy. Nominal camera alignment does not establish likeness or anatomical correctness. Route required rig/animation work through subject-specific skills with evidence before declaring readiness.
9. Use `record` for current independent reviewer and separate human acceptance/rejection receipts. Check `status`; changed inputs invalidate affected proofs, approvals and dependent results. Use `promote` only after explicit current human acceptance and task authorization.

For model-to-animation production, hand the reviewed model to `build-model-animations`. Preserve original-only classification as source evidence; record new topology/articulation findings separately. Animation readiness may require neutral-pose or geometry repair work, especially fused limbs/equipment. Its motion package and complete-clip/runtime review do not inherit proof-set or static-asset acceptance.

## Guardrails

- Use the exact initialized and explicitly built `runtime/bubo` dependency through Hephaera's verified launcher. No sibling checkout or source-run fallback is allowed. Native process guards are not an OS sandbox.
- No threshold matte fallback, placeholder stages, automatic human approval, hidden downloads, silent pipeline changes or unreviewed promotion.
- Keep stage state under `.hephaera/.cache/tasks/<task>/`, candidates under `.art-staging/proof-to-model/`, tools under ignored `.local/tools/proof-to-model/`, and reviewed runtime packages under `assets/models/`.
- Preserve failed attempts and immutable originals, hashes, model/tool/script/recipe identity and logs. An exhausted finishing budget requires an actual human decision and a current hash-bound `--finish-budget` receipt for exactly one more attempt; never reset counters or manufacture approval. Distinguish simulated-process tests from live engine and Blender acceptance.
- Large solver inputs may use explicitly selected, measured `quadriFlow.simplification` with world-box vertices held by exact identity/coordinate checks, per-part input caps and full vertex/surface error checks. Preserve source preparation and all topology/component guards; never increase tolerances or caps automatically. Smaller input does not bound QuadriFlow's internal growth or certify visual quality.
- Generated/revised proofs and reconstruction renders never become classification evidence. Hidden anatomy and unseen surfaces remain inferred design completions after approval.
- Single-view diagnostics require explicit `--mode single-view-diagnostic` and use the separate `proof` approval kind; that receipt cannot approve a production proof set. A four-image subset cannot satisfy six-view. Only a separately qualified, explicitly registered four-view production profile accepts its own complete four-image set; no SV fallback, duplicate views, contact sheet, omitted-slot aliases or copied cross-profile approvals.
- Preserve old manifests, grants, source/classification/generation history and installed dependency/license identities. Use fresh versions for profile/build migration. Four-view reuse is initially unavailable; do not copy stages or approvals from six-view donors. Structural or simulated tests never establish actual four-view inference, riggability, performance or human acceptance.
