# Local HTTPS for my.hephaera.com

Status: proposal, not implemented. The approved immediate change is documentation only. Keep the existing authenticated `http://127.0.0.1:<port>` viewer until HTTPS is ready; this document does not authorize certificate installation, DNS changes or a hosted service.

## Address and trust model

The target browser URL is `https://my.hephaera.com:<port>`. The Node service must still bind explicitly and exclusively to IPv4 `127.0.0.1`, never to the hostname, `0.0.0.0`, a LAN address or IPv6. Preserve one server per project and ephemeral unprivileged ports. DNS cannot select a port, so a bare `https://my.hephaera.com` without a port is not part of the first release; a shared port 443 router would be a separate project.

On 2026-11-12, checks through two public recursive resolvers returned A `127.0.0.1` and AAAA `::1`. These are dated observations, not a guarantee of future DNS or evidence of Cloudflare account settings. The initial profile should use DNS-only A `127.0.0.1`; diagnose the existing AAAA record and request its removal before switching, rather than introducing an IPv6 listener. Normal startup must never edit DNS, system resolver settings or hosts files. A blocked or altered DNS result must produce a clear diagnostic.

Cloudflare can supply DNS, but [Flexible SSL terminates TLS at Cloudflare](https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/flexible/), which cannot proxy to each user's own loopback interface. A [DNS-only record](https://developers.cloudflare.com/dns/proxy-status/) leaves the browser connecting directly to the local server, so that server needs its own trusted certificate. [Cloudflare Origin CA certificates](https://developers.cloudflare.com/ssl/origin-configuration/origin-ca/) are not a substitute for ordinary browser trust.

The current runtime intentionally rejects hostname aliases through endpoint and exact Host/Origin validation. Merely changing the URL causes `Invalid request origin.`; removing those protections is not a migration strategy. A custom HTTP hostname also has different browser trust/HTTPS-upgrade behavior from literal loopback, so do not switch the current HTTP viewer to the domain as an intermediate step. See [Chromium's HTTP guidance](https://chromium.googlesource.com/chromium/src/+/main/docs/security/ask-before-http/ask-before-http-adoption-guide.md).

## Recommended first release: explicit certificate setup

Start with certificate import and an explicit local-development trust setup, followed by ordinary unattended startup. Support the exact shared hostname without distributing a shared private key or giving users access to the domain's DNS credentials.

| Certificate source | Intended use | Setup and limits |
| --- | --- | --- |
| Organization-managed CA | Managed developer machines | Import a unique per-installation leaf/key for `my.hephaera.com`; the selected browser must already trust the organization's issuer |
| Explicit local development trust | Individual developer installations | Generate a unique local identity and obtain one-time approval for the exact trust-store change; validate the chosen OS/browser independently |
| Owner-operated ACME DNS-01 | Domain owner's pilot installation | Issue with a locally generated key and narrowly scoped DNS validation; issuance/renewal is a separate configured operation |
| Public issuance for general distribution | Later product phase | Requires a separately reviewed enrollment service, installation identity, rate capacity, abuse controls and likely distinct installation hostnames |

For the local-development profile, prefer an exact-name, separately trusted leaf where the target platform/browser can support and renew it safely. If an issuing local CA is needed, explicitly review its broader signing authority, protect its private key and obtain separate trust approval. Do not assume name constraints or user-level trust behave consistently across platforms. Select and verify the trust backend before claiming automatic renewal or support. The first milestone may provide managed-certificate import while local trust backends remain unavailable.

[mkcert](https://github.com/FiloSottile/mkcert) is a useful manual developer option and design reference, not an embedded general-user installer: its documentation cautions against end-user deployment and sharing CA keys. Never download it or install a root during routine startup. [Let's Encrypt's local-certificate guidance](https://letsencrypt.org/docs/certificates-for-localhost/) also explains why shipping an app with one public certificate/private key is unsafe. Each installation must generate or receive its own key through its selected setup process.

## Implementation sequence

1. **Separate browser identity from socket binding.** Add an exact, code-owned `my.hephaera.com` HTTPS profile while keeping the bind address constant. Version runtime metadata to record transport, browser origin, literal connection endpoint, certificate identity and setup ownership. Allow no arbitrary hostname, wildcard Host check, custom bind address or external probe URL. Keep existing HTTP and legacy-owned shutdown compatibility explicit.
2. **Add certificate inspection and setup.** Proposed interfaces are `session-visualizer.sh tls status`, `tls import`, `tls setup` and `tls uninstall`; these commands do not exist yet. Validate finite file sizes, regular unlinked files, key/certificate match, exact DNS SAN, server-auth usage, validity, chain and selected issuer/trust profile before activation. Copy admitted material into protected `.hephaera/.cache/visualizer/private/tls/`; do not serve it, log keys, pass PEM values in argv or commit it. Setup/trust writes require an explicit user-selected operation and applicable OS prompt; normal `start` installs nothing.
3. **Implement local HTTPS and trusted opening.** Use Node.js 24's built-in HTTPS/TLS APIs with TLS 1.2 minimum. Check the actual listening socket and both socket addresses remain IPv4 loopback. Require exact SNI/Host/Origin for the selected profile and port, retaining bearer authentication, read-only routes, CSP, bounded SSE and the asset allowlist. Health connects directly to `127.0.0.1`, sets the expected TLS server name/Host, validates the admitted trust chain and exact identity, bypasses proxies and follows no redirects. Never use `rejectUnauthorized:false` or browser certificate/security exception flags. Node probes need their own explicit trust configuration; browser trust alone is not proof they work.
4. **Prevent DNS or origin changes from carrying credentials elsewhere.** Verify DNS prerequisites before issuing an authenticated browser bootstrap. Prove that the supported isolated Chromium launch keeps this exact hostname connected to `127.0.0.1`, including Secure DNS, mixed answers and rebinding tests; do not rely on a one-time lookup. Evaluate a narrowly scoped browser resolver mapping as a tested mechanism, without disabling browser security. If routing cannot be guaranteed, report the HTTPS profile unavailable. Do not send the capability to a remotely resolved address or a redirect. Capabilities remain in the private bootstrap fragment and selected origin's session storage; never transfer a bearer through a query string or cross-origin redirect.
5. **Add renewal, replacement and recovery.** Record only non-secret issuer/certificate fingerprints, validity, ownership and renewal status. Renew ahead of expiry through the explicitly selected backend; do not run ACME on every `start` or assume fixed certificate lifetimes. Validate a complete replacement before atomic activation, retaining the previous still-valid identity on failed renewal. Do not reuse an expired/untrusted certificate or silently downgrade a selected HTTPS profile to HTTP. Show the specific certificate/DNS/trust/ESET limitation while collection and agent work continue. Uninstall removes only the exact owned trust entries/material after confirming no dependent viewer remains; never remove unrelated certificates or session history.
6. **Migrate existing installations safely.** Stop the owned viewer before baseline source updates, acquire the maintenance write lease, then reopen the same session UUID. Preserve events, Goal state, fences and approvals byte-for-byte. Open a fresh authenticated bootstrap for the new HTTPS origin; the old HTTP origin's session storage does not carry over. Keep HTTP as a separately explicit opt-out profile, never an automatic TLS failure fallback. Parallel projects retain distinct ports, credentials and ownership.

An ESET exception may prevent inspection of this hostname, but it neither creates a certificate nor makes it browser-trusted. Treat interception, trust and DNS failures separately. Hephaera should diagnose the observed failure without editing antivirus settings, relaxing verification or requiring every user to disable inspection.

## ACME and general distribution boundary

[DNS-01](https://letsencrypt.org/docs/challenge-types/#dns-01-challenge) can validate a domain even when its service is private. Keep Cloudflare credentials with the domain operator or an isolated issuance service, with challenge-only delegation where possible; never bundle a zone token in Hephaera. For the owner's pilot, the existing A record can remain loopback while ACME validates a TXT challenge. Do not use public HTTP-01 or expose the viewer for validation.

Issuing the same hostname independently for every user is not a scalable default: [CA issuance limits](https://letsencrypt.org/docs/rate-limits/) apply, and independent certificates for a shared public name also share that name's impersonation scope. A later public-trust design should assign a unique installation hostname such as `INSTALLATION_ID.my.hephaera.com`, generate its key locally, and send only a proof-of-possession CSR to an authenticated operator-controlled issuer. This requires additional DNS and differs from the exact shared-hostname local-trust profile. Review registered-domain limits, onboarding quotas, revocation, renewal authorization, privacy, account recovery and CA terms before selecting it. No hosted issuer is included in the first local release.

## Acceptance and delivery order

Deliver address/runtime validation first, then certificate import/inspection, an explicit approved trust backend, HTTPS opening, renewal/recovery and session migration. Use synthetic identities and ACME staging while testing. Keep implementation and package publication separate from this proposal.

Acceptance requires native Windows, Linux and macOS evidence for actual `127.0.0.1`-only sockets, rejected IPv6/LAN/proxy/rebinding access, unauthorized and foreign-origin rejection, and browser opening without certificate warnings or exception flags. Include expired, untrusted, wrong-SAN, mismatched-key and intercepted certificates; offline startup; DNS missing/A+AAAA/changed answers; interrupted renewal; denied trust prompts; uninstall ownership; concurrent projects; server restart; SSE reconnect and replay. Verify the real browser's peer and rendered state, not just a Node health request.

Complete a real instrumented session through verification, preserve its replay and history through HTTP-to-HTTPS migration, and repeat the existing 10000-event freshness check. Report support per tested OS/browser; do not infer native trust support from mocks or another platform. Keep current authenticated loopback HTTP as the documented working profile until these gates pass.
